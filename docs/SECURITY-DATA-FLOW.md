# Personal data flow and retention

Reviewed 16 October 2026 against the supplied five security prompts and the security video. This map describes actual application flows rather than a legal compliance certification.

| Collection point | Data and destination | Controls and retention |
| --- | --- | --- |
| Signup, login and recovery | Name and email go to owned Supabase Auth/profile records. Password goes over HTTPS to Supabase Auth. | Supabase hashes user passwords with bcrypt. Passwords are not stored by application tables or browser persistence. Verified email creates only a Student role. Registration metadata cannot promote a user. |
| Browser authentication | Session access/refresh tokens and SDK identity are held in current-tab storage, with a memory fallback. | The exact legacy project auth key is removed from localStorage during migration. Session storage is still accessible to same-origin JavaScript; this is not HttpOnly cookie authentication. Closing a tab may require a new login. Academic work remains in the database. |
| Proposals, milestones and peer evidence | Shared group proposal text, private uploads, contributions, assessment information and acknowledgements go to owned PostgreSQL/private Storage. | Role and group ownership checks, active-session checks, immutable files, server content verification and expiring document links. Peer evidence and unpublished results remain role scoped. |
| Gemini assistants | Selected authorized proposal text, supported document bytes/text, health/reminder evidence, relevant scheduling context, session SQL totals or the support question. | Explicit drafting consent, database role/context checks before export, bounded requests/responses, persisted budgets, output schema/reference validation and human approval for academic actions. Account passwords, SMTP credentials, keys and the privacy-request queue are not exported. |
| External source screening | Public keywords or a fallback proposal title go to Europe PMC, Crossref and Wikipedia. Short retrieved passages and proposal abstract go to Gemini. | Separate consent; fixed provider endpoints; no arbitrary URL fetch or redirect following. Bounded coverage, not a full-web plagiarism certification. |
| QA assistant | A fixed approved selection of source excerpts and sanitized test evidence goes to Gemini. | Exact checksum approval; the snapshot is not automatically refreshed by this security release. It is not an independent or current whole-project security audit. |
| Invitations, verification and recovery mail | Recipient address and authentication message go through configured Gmail SMTP via Supabase Auth. | Single-use managed email verification/recovery links, 15-minute expiry, verified sender, TLS. User creates their own password. |
| Reminder email | The selected authorized reminder or fixed delivery-test text goes to the verified registered recipient through the Vercel Gmail SMTP API. | Explicit approval, server-selected recipient, eligibility and opt-out recheck, persisted attempt claim, no automatic resend after an uncertain SMTP attempt. |
| Service enquiries | Name, email, chosen plan, brief and follow-up consent go to private enquiry tables. | Coordinator access, bounded inputs, persistent abuse limits, keyed email pseudonym rather than raw address in abuse counters. No payment details are collected. |
| Error monitoring | Fixed error category, random reference and minimal timestamps go to the owned database/logs. | Raw exceptions, URLs, documents, email addresses, request bodies, passwords and keys are excluded from application error telemetry. Platform access logs are controlled separately by Supabase/Vercel. |
| Data requests | Own export, correction or deletion-review request and coordinator response go to a private queue. | Caller identity is bound to the approving token. Other students cannot read it. Only coordinators respond. Duplicate open types and a five-per-day quota prevent abuse. No mail or AI export occurs. |

## Retention and erasure

Data requests are an auditable review workflow, not automatic account deletion or a complete self-service export. An institution must decide academic and legal retention obligations, verify the requester, prepare a secure export/correction or perform approved erasure/anonymization, and record what was actually done. A coordinator response must not claim erasure unless it was separately verified. The portal deliberately does not silently delete proposals, assessment evidence or shared academic records.

Persistent private demo credential handovers are operational secrets, not the user password database. Keep them out of shared source archives and rotate or disable demo staff access before enrolling unrelated client users. Public demo screens use synthetic data; a privileged demo account in the production project is not tenant isolation.
